# Проверка информационной архитектуры LexiGo

Документ фиксирует воспроизводимый протокол проверки Issue #61. Автоматические тесты подтверждают техническую доступность путей, но не заменяют модерируемые сессии с новыми пользователями.

## Цель

Проверить, что пользователь без подсказки понимает назначение четырёх верхнеуровневых разделов:

- **Главная** — одно приоритетное следующее действие;
- **Обучение** — настройка режима, состава и размера урока;
- **Словарь** — поиск и просмотр слов, терминов и рабочих фраз;
- **Прогресс** — результаты, очередь повторения и дневная цель.

## Участники

Минимум 5, целевое количество 7 новых пользователей, которые ранее не работали с текущей версией LexiGo. Не включать разработчиков и авторов интерфейса.

Рекомендуемая матрица:

- 2 пользователя iPhone PWA;
- 1 пользователь Android;
- 1 пользователь tablet/landscape;
- 1–3 пользователя desktop.

## Методика

Сессия проводится без предварительного объяснения структуры приложения. Модератор читает только формулировку задачи и не подсказывает название раздела или элемента управления.

Для каждой задачи записываются:

- успешность без подсказки;
- время до первого правильного действия;
- количество переходов между верхнеуровневыми разделами;
- количество немедленных возвратов A → B → A;
- первая произнесённая интерпретация назначения экрана;
- причина ошибки или сомнения.

## Задачи

### 1. Начать рекомендуемое действие

Формулировка: «Откройте приложение и начните то занятие, которое оно рекомендует сейчас».

Критерий успеха: пользователь использует единственный основной CTA на Главной без перехода по нескольким конкурирующим карточкам.

### 2. Настроить новый урок

Формулировка: «Подготовьте урок на 15 элементов в режиме самостоятельного воспроизведения».

Критерий успеха: пользователь переходит в «Обучение», выбирает режим и размер, понимает состав до запуска.

### 3. Найти конкретное слово

Формулировка: «Найдите слово rollback, откройте его перевод и пример».

Критерий успеха: пользователь открывает «Словарь», использует поиск и карточку слова без входа в composer урока.

### 4. Найти рабочую фразу

Формулировка: «Найдите готовую формулировку для сообщения об инциденте».

Критерий успеха: пользователь открывает «Словарь», переключается на «Рабочие фразы» и находит карточку.

### 5. Настроить урок из каталога

Формулировка: «После просмотра материала подготовьте урок по этой теме».

Критерий успеха: каталог переводит пользователя в «Обучение» с уже выбранным типом материала и темой; повторный выбор темы не требуется.

### 6. Проверить результат обучения

Формулировка: «Посмотрите, сколько материалов сейчас нужно повторить и как выполнена дневная цель».

Критерий успеха: пользователь сразу выбирает «Прогресс» и находит обе метрики.

## Порог принятия

Issue #61 может считаться полностью проверенным только при выполнении всех условий:

- не менее 80% участников выполняют задачи 1–4 без подсказки;
- медианное время задачи 1 — не более 15 секунд;
- медианное время задачи 3 — не более 30 секунд;
- не менее 80% участников корректно описывают назначение «Обучения» и «Словаря»;
- доля немедленных возвратов между разделами не превышает 15% переходов в сессиях;
- ни один участник не воспринимает каталог как второй экран настройки урока.

## Телеметрия

Endpoint `/api/v1/product/journey` сохраняет только allow-listed переходы и coarse-контекст устройства. Событие содержит `fromRoute`, `toRoute`, `intent` и признак немедленного возврата. В таблице отсутствуют user ID, session ID, IP, URL, query, referrer, search text, email, cookie и raw User-Agent.

Для сравнения до/после использовать view `product_navigation_daily`:

```sql
select
    event_date,
    from_route,
    to_route,
    intent,
    is_backtrack,
    sum(transition_count) as transition_count
from product_navigation_daily
where event_date >= current_date - interval '14 days'
group by
    event_date,
    from_route,
    to_route,
    intent,
    is_backtrack
order by
    event_date,
    transition_count desc;
```

## Release gate

Автоматический gate и human validation являются двумя независимыми обязательными слоями:

1. Полная CI-матрица должна пройти backend unit и integration, frontend lint, typecheck, unit, production build, browser e2e, WebKit/PWA, accessibility, visual regression, performance budgets, container builds и очистку self-hosted runner.
2. После зелёного технического gate PR может быть объединён и развёрнут в dev/stage для модерируемой проверки. Merge не закрывает Issue #61 автоматически.
3. На проверенной dev/stage-сборке должны быть проведены 5–7 модерируемых сессий по протоколу выше.
4. Зелёный CI подтверждает техническую корректность реализации, но сам по себе не закрывает Acceptance Criteria, связанные с пониманием интерфейса реальными новыми пользователями.
5. Issue #61 и публичный release gate остаются открытыми до появления обезличенного human evidence и выполнения порогов принятия.

## Release evidence

К Issue приложить:

- ссылку на зелёный CI итогового commit SHA;
- commit SHA и адрес dev/stage-сборки, использованной в сессиях;
- обезличенную таблицу результатов 5–7 сессий;
- агрегированные показатели по задачам;
- список обнаруженных неоднозначностей;
- решение по каждой неоднозначности: исправлено в текущей задаче либо вынесено в отдельный Issue;
- ссылку на период данных `product_navigation_daily`, использованный для сравнения.
