# Frontend async-state contracts

LexiGo отображает асинхронные состояния локально, рядом с ресурсом или действием, которое их вызвало. Сбой одного ресурса не должен скрывать или блокировать уже загруженные данные других панелей.

## Состояния

- `loading` — загрузка продолжается; используется локальный skeleton или компактная status-панель с `aria-busy`.
- `empty` — запрос завершён успешно, но данных нет; состояние содержит понятное объяснение и следующее действие.
- `error` — запрос завершён ошибкой; сообщение локализовано, не содержит внутренних stack traces и при возможности предлагает `Повторить`.
- `success` — подтверждённое сервером состояние, когда требуется отдельная итоговая панель.

Компоненты находятся в `frontend/components/async-state.tsx`.

## Классификация ошибок

`frontend/lib/request-failure.ts` разделяет:

- истёкшую сессию (`401`);
- ограничение доступа (`403`);
- отсутствие сети;
- timeout;
- malformed или несовместимый payload;
- client error;
- server error;
- неизвестную ошибку.

Пользовательский текст строится через `describeRequestFailure`. Raw backend message, HTTP status и внутренние детали не выводятся. Для обращения в поддержку допускается безопасный correlation ID из `X-Request-ID`, `X-Correlation-ID` или `traceparent`.

## Accessibility

- ошибки используют `role="alert"` и assertive announcement;
- loading, empty и success используют `role="status"`;
- error/empty результат получает программный focus;
- retry остаётся обычной keyboard-accessible кнопкой;
- skeleton не передаёт декоративные элементы screen reader;
- shimmer отключается при `prefers-reduced-motion`.

## Правила интеграции

1. Не использовать полноэкранный spinner для частичной загрузки.
2. Не очищать успешные соседние ресурсы при retry одной панели.
3. Не подставлять вымышленные значения во время loading/error.
4. `404` трактовать как `empty` только когда отсутствие ресурса является допустимым доменным состоянием.
5. Внешний JSON валидировать до записи в React state.
6. Retry должен повторять только упавший запрос.
7. Новые сценарии покрывать browser-тестами как минимум для Chromium и WebKit; device-specific риски включать в мобильную матрицу.

## Тестовый контракт

`frontend/e2e/async-states.spec.ts` фиксирует регрессии для slow response, timeout, offline, истёкшей сессии, `404`, `500`, empty response, локального retry и сохранения успешно загруженных панелей.

Browser-тесты должны находить состояние по semantic role и доступному имени, например `getByRole("alert", { name: "Ошибка текущего действия" })`. CSS-классы допустимы для оформления и обратной совместимости, но не являются стабильным пользовательским контрактом теста.
