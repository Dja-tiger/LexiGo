# Offline-safe lesson reviews

## Назначение

LexiGo сохраняет оценку текущей карточки в IndexedDB **до** первого сетевого запроса. Потеря сети, timeout, закрытие вкладки или завершение iOS PWA не требуют повторно отвечать на карточку.

Полный offline-урок намеренно не реализован: переход к следующей карточке разрешается только после подтверждённой сервером позиции урока. Это сохраняет единый источник истины и не создаёт расхождение между устройствами.

## Клиентский lifecycle

1. Frontend распознаёт только `post /api/v1/lessons/{lessonID}/words/{wordID}/review`.
2. Перед отправкой создаётся durable-запись в IndexedDB `lexigo-review-outbox`.
3. Логическая операция дедуплицируется по `userId + lessonId + wordId + lessonVersion`.
4. Для операции генерируется стабильный UUID и передаётся как `Idempotency-Key`.
5. При offline, timeout или `5xx` запись остаётся в состоянии `pending`.
6. Retry запускается при событии `online`, возврате вкладки в `visible` и при следующем восстановлении сессии.
7. После `2xx` запись становится `synced`; приложение показывает краткое подтверждение и перезагружает серверный snapshot урока и прогресс.
8. Неретраебельные `4xx`/`409` становятся `failed`; пользователь принимает актуальное серверное состояние вместо бесконечного replay.

Runtime отслеживает успешные login, registration, refresh и logout в текущей вкладке. Поэтому очередь начинает работать сразу после входа без reload и прекращает использовать сессию сразу после logout.

Access token и CSRF token в IndexedDB не сохраняются. Retry использует текущую восстановленную HttpOnly-cookie session и новый access token.

## Серверная идемпотентность

Backend принимает необязательный заголовок `Idempotency-Key` в формате UUID. Старые клиенты без заголовка продолжают работать по прежнему контракту.

Для нового клиента backend:

- вычисляет SHA-256 fingerprint ресурса и нормализованного review payload;
- возвращает сохранённый response для идентичного replay;
- отклоняет повторное использование ключа с другим payload кодом `idempotency_key_reused`;
- использует существующую блокировку строки `lesson_sessions`, поэтому конкурентные запросы не создают два `review_events`;
- при обрыве после commit, но до сохранения idempotency response проверяет точный `review_events` и восстанавливает исходный `LessonReviewResult`.

## Конфликты между устройствами

Оптимистическая версия урока остаётся обязательной. Если другое устройство сохранило другую оценку или продвинуло урок, queued review получает conflict и не повторяется автоматически. Frontend показывает состояние `failed` и предлагает загрузить актуальный server snapshot.

Если другое устройство сохранило эквивалентный review для той же версии и карточки, backend может восстановить тот же результат без создания второго learning event.

## Хранение и очистка

- Клиентские `pending` и `failed` сохраняются до синхронизации или явного разрешения конфликта.
- Клиентские `synced` записи остаются локально до 24 часов для диагностики response-loss сценариев, затем удаляются.
- Данные IndexedDB разделены по `userId`; очередь одного аккаунта не отправляется с токеном другого аккаунта.
- Серверный idempotency response хранится 30 дней. Просроченные строки исключаются из replay и удаляются небольшими индексированными batch при последующих review-записях.
- После истечения TTL UUID можно безопасно использовать для новой логической операции; normal clients всё равно генерируют новый UUID для каждой карточки.

## Release checks

Обязательные сценарии:

- offline до клика по rating;
- автоматический replay после события `online`;
- потеря response после серверного commit;
- закрытие вкладки/PWA с `pending` записью;
- вход из гостевого состояния без перезагрузки;
- replay с тем же `Idempotency-Key`;
- concurrent replay создаёт один `review_events`;
- reuse ключа с другим payload возвращает `409`;
- expired key может быть использован для новой операции;
- Chromium desktop и iOS WebKit.
